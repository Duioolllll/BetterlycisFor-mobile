# 핵심 서비스 I/O·처리 최적화

검토일: 2026-10-23. 기준 소스: `8a12f2a31f4c1d32870bc7b3f281092e560b8379` (0.4.2).
이 최적화는 0.4.3 릴리스 APK에 포함한다. [0.4.3 배포·검증 기록](RELEASE-0.4.3.md)과 Release에 첨부한 실제 검사 결과를 함께 확인한다.

## 확인한 비용과 변경

| 경로 | 기존 동작 | 변경 |
| --- | --- | --- |
| `AudioSignal.pcm/visualizer` | 프레임마다 대역 배열 3개 생성, 주파수→대역 로그 계산, PCM Hann window 코사인 계산 | 입력 형식별 대역 인덱스/개수와 고정 window를 계산해 재사용. 작업 배열 재사용. 외부로 전달하는 Frame의 bands 복제는 유지 |
| `AppState` 재생 정보 | 화면의 50ms 오디오 tick, 500ms 진행도 tick, 플로팅 가사에서 `MediaController.getPlaybackState()` 반복 | 세션 선택/콜백에서 받은 최신 sample을 저장하고 기존 시간 보간식에 사용 |
| `LyricsListener` 진행도 콜백 | 동일 곡에서도 앨범 아트 후보·알림 조회 및 전체 snapshot 전송 | 동일 세션의 진행도/속도/재생 동작 sample은 기존 경량 tick 경로 사용. 알림에 같은 메타데이터가 반복돼도 전체 snapshot은 생략. 곡·길이·재생/정지·소스 목록·새 이미지 변화는 전체 snapshot 유지 |
| `MainActivity` 상태 알림 | 한 main-loop 안의 중복 emit마다 JSON snapshot 작성·WebView 전송 | 대기 중인 전체 publish를 한 번으로 합침. 콜백이 몰릴 때 진행도 패킷을 50ms 간격으로 합침(평상시 500ms tick 유지) |
| 앱 이름·플로팅 가사 | 세션 선택 때마다 앱 라벨 조회, 150ms마다 동일 텍스트 설정 | 앱 라벨 최대 32개 보관(서비스 정리 시 초기화), 텍스트/투명도가 달라질 때만 뷰 변경 |
| 가사·이미지·파일·캐시 입력 | 서로 다른 읽기 루프와 일부 읽기 경로의 늦은 취소 확인 | `IoSupport.read` 공유. 읽기 전후 interrupt 확인, 최대 크기를 한 바이트 초과하면 즉시 거부, 네트워크/불러오기 읽기에 20초 경과 검사 |
| HTTP 응답 | 본문을 읽은 뒤 크기 제한 판단 | Content-Length가 제한을 넘으면 본문을 읽기 전에 거부. 길이 누락/거짓 값은 실제 읽기에서도 검사 |
| 수동 검색·불러오기 | 이전 수동 검색/파일 읽기가 작업 큐에 남음, 작업 중 Song 공유 | 이전 Future 취소, 취소된 큐 항목 제거. 검색/불러오기에 곡 정보 사본 전달. 곡 전환 시 이전 수동 검색도 취소 |
| 가사 캐시 저장 | 같은 곡의 `.tmp` 이름 공유, 저장마다 디렉터리 조회 | 고유 임시 파일과 동일 디렉터리 이동으로 교체, 읽기/쓰기/삭제 잠금. 기존 파일 교체는 전체 목록 조회 생략. 신규 파일만 200개 한도 검사, 정렬 전 mtime을 파일당 한 번 조회 |
| EAPI·캐시 파일명 hex | 바이트마다 `String.format` 객체 생성 | 문자 배열 변환. 대소문자/leading zero와 기존 캐시 이름 보존 |

기존 읽기 크기 제한(가사 HTTP/캐시 3MiB, 이미지 8MiB, 불러오기 2MiB), 가사 매칭·한국어 원문 선택·싱크 계산·오디오 분석 수식·UI는 유지한다. 캐시에 저장할 직렬화 결과가 3MiB를 초과하면 저장하지 않는다.

## 측정 결과

[실행 결과 JSON](performance/service-io-2026-10-23.json). Linux x86_64, OpenJDK 17.0.20, 워밍업 후 7회 측정의 중앙값. 동일 JVM 안에서 이전/이후 실행 순서를 번갈아 측정했다. PCM/Visualizer는 회당 2,000프레임, hex는 회당 200회다. 프레임 측정에는 새 분석기의 최초 형식별 대역 준비 비용도 포함한다.

| 작업 | 기존 중앙값 | 변경 중앙값 | 처리 시간 감소 | 기존 할당/회 | 변경 할당/회 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PCM 2048 samples, 44.1kHz | 68.37µs | 35.14µs | 48.6% | 440B | 138.06B |
| Visualizer 1024 bytes, 44.1kHz | 13.62µs | 6.08µs | 55.3% | 440B | 137.03B |
| 256-byte uppercase hex | 110.58µs | 3.59µs | 96.8% | 158,712B | 1,640B |

이 값은 특정 Linux JVM의 마이크로벤치마크다. Android ART, 휴대폰 CPU, 실제 앱 지연·배터리 개선율을 나타내지 않으며 CI의 시간 임계값으로 사용하지 않는다.

## 실제 검증

- 변경 전 기본 오프라인 검사: 190개 통과.
- 변경 후 기본 검사와 신규 I/O 검사: 214개 통과(기존 190 + 신규 24).
- 원본 Git 소스와 변경 AudioSignal 비교: PCM/Visualizer/정지 2,073프레임의 필드·대역·sequence·timestamp가 비트 단위 동일. 여러 sample rate, FFT 크기, 부분 PCM 입력, 정지 전환 포함. 재사용한 작업 배열이 이전 Frame을 바꾸지 않음도 확인.
- 신규 I/O 검사: UTF-8 분할 입력, 정확한 크기 경계, 초과 입력의 1바이트 probe, 소유권, 읽기 전/중 취소, 진행 없는 stream의 시간 제한, 전체 바이트 범위의 hex 호환성, 병렬 캐시 교체/읽기, 취소된 저장의 기존 데이터 보존, 캐시 200개 한도·삭제, 부모 작업 취소의 양쪽 제공처 전파.
- Android API 36 대상 전체 Java 컴파일·DEX·리소스 패키징 및 Debug APK 서명 검증 통과. Debug 산출물은 배포용 업데이트 APK가 아니다.
- 브라우저 UI/가사 흐름 smoke는 실행을 시도했으나 Chromium이 없고 공식 다운로드 ZIP이 손상된 상태로 반환되어 실행하지 못했다. 이번 변경에서 웹 UI 자산은 변경하지 않았다.

## 재현 명령

```bash
python3 tools/test.py --sdk /absolute/path/to/Android/Sdk
python3 tools/benchmark-service.py --baseline 8a12f2a31f4c1d32870bc7b3f281092e560b8379
python3 tools/build.py --sdk /absolute/path/to/Android/Sdk --variant debug
```

벤치마크는 Git 기준 커밋의 AudioSignal을 별도 클래스명으로 컴파일해 비교한다. 얕은 clone에 기준 커밋이 없다면 해당 Git 이력을 먼저 fetch해야 한다. 벤치마크 결과는 `build/service-benchmark.json`에 저장하며 기본 회귀 검사에는 실행 시간을 측정하는 검사를 넣지 않는다. `--check-only`는 성능 측정을 생략하고 출력 동등성만 확인한다. `Service I/O and processing checks` Actions는 비밀 서명 키 없이 기본 검사·출력 동등성·Android 컴파일·APK 패키징 검사를 실행한다.

## 미검증·남은 한계

- 실제 Android 기기에서 미디어 세션 콜백, 음악 앱별 한국어 싱크·앨범 아트·오디오 캡처·플로팅 가사, Android 16 설치/업데이트, 배터리·프레임 지연은 이번 변경으로 재검증하지 않았다. 이전 APK의 설치 성공을 이번 소스의 성공으로 간주하지 않는다.
- timeout/interrupt 검사는 블로킹 `read()` 자체를 강제로 중단시키지 않는다. HTTP의 기존 connect/read timeout(가사 8초, 이미지 5초)은 유지되며, Android content provider가 응답하지 않으면 해당 읽기가 반환할 때까지 취소가 지연될 수 있다. 연결/응답 헤더 대기를 포함한 전체 작업의 20초 절대 상한을 보장하지 않는다.
- 최적 결과 검색은 여전히 양쪽 가사 제공처 결과를 기다린다. 더 빠른 제공처 결과를 먼저 표시하는 정책 변경은 포함하지 않는다. 실제 제공처 네트워크 호출은 이번 검증에서 실행하지 않았다.
- 전체 snapshot이 필요한 메타데이터/가사/설정 변경에서는 기존 가사 JSON과 커버가 전송된다. 경량 경로가 모든 이벤트의 payload를 없애는 것은 아니다.
- atomic move를 지원하지 않는 파일시스템은 replace move로 대체한다. 내부 저장소 외의 모든 파일시스템에서 원자성/전원 손실 내구성을 보장하지 않는다.
